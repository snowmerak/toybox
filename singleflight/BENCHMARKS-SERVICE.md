# 다중 키 · 신규/중복 혼합 서비스형 부하

## 목적과 범위

기존 독립 키·단일 핫 키·순환 키 벤치마크를 보완합니다. 다수 클라이언트가
매 요청마다 키를 바꾸고, 서로 다른 키의 실행과 동일 키의 중복 요청이 동시에
섞이는 상황을 비교합니다. 공개 구현·API·기본 WaitGroup 선택은 변경하지 않았습니다.

구현: [service_benchmark_test.go](service_benchmark_test.go).
데이터 생성·신규 키 유일성·히스토그램은
[service_benchmark_helpers_test.go](service_benchmark_helpers_test.go)로 검증합니다.

## 부하 모델

클라이언트 64개 또는 1,024개가 이전 결과를 받은 즉시 다음 요청을 보냅니다.
요청 사이의 sleep/think time은 없습니다. 동시 요청은 클라이언트 수로 제한합니다.
각 클라이언트는 하나의 키에 고정되지 않으며, 총 요청 수는 정확히 Go benchmark의 N입니다.
모든 실행은 종료 후 drain됩니다. 기다리지 않은 요청·누락된 결과로 빨라질 수 없도록
모든 키에 대응하는 반환값과 오류를 검사합니다.

**포화 closed-loop 모델**입니다. 응답과 무관한 일정 도착률, 무한 대기열,
네트워크 서버 또는 실제 DB/API 부하를 구현한 것은 아닙니다. 처리량은 이 조건의
완료율이고, 지연은 라이브러리 호출 시작부터 결과 수신까지입니다. 입장 대기열이나
응답이 느려진 동안 추가로 도착했을 요청의 지연은 포함하지 않습니다
(coordinated omission 가능). 아직 주어진 실제 서비스 트래픽이 없으므로 아래는
재현 가능한 합성 시나리오이지 실서비스 수용량의 보장이 아닙니다.

| 시나리오 | 재사용 키 선택 | 매번 새 키 선택 확률 |
|---|---|---:|
| Uniform4096New50 | 4,096개 키에서 균등 선택 | 50% |
| Zipf4096New10 | 4,096개 키의 Zipf(s=1.2, v=1) 편중 | 10% |
| Hot32New20 | 재사용 요청의 90%는 인기 32개, 10%는 전체 4,096개 | 20% |

Hot32는 전체 요청 기준 약 72% 인기 키 / 8% 넓은 풀 / 20% 신규입니다.
같은 키를 고르는 비율과 실제 중복 병합 비율은 다릅니다. 이전 실행이 이미 완료됐다면
같은 키라도 새 백엔드를 실행합니다. 신규 키는 큰 유한 풀의 재사용이 아니라
클라이언트 ID와 요청 순번으로 만들어 **실행 내에서 한 번만 사용**합니다.
풀과 신규 키는 모두 길이 21바이트이며, 반환값도 키마다 다릅니다.

- PRNG: math/rand/v2 PCG, seed `0x5eed20261004`, 클라이언트 ID를 두 번째 seed로 사용.
- 클라이언트마다 미리 생성한 1,024개 선택 템플릿을 반복합니다. 신규 키의 순번은
  템플릿 반복과 무관하게 계속 증가합니다. 템플릿은 시간 순서의 실제 트래픽 기록은 아닙니다.
- Do 80% / DoChan 20%를 목표 확률로 섞으며, **두 API는 같은 그룹**을 사용합니다.
  DoChan 호출자도 자신의 결과를 기다립니다. 취소·수신 포기·Forget·오류 폭주는 이 부하의 범위 밖입니다.
- 요청 키 풀·템플릿·통계 버퍼·클라이언트 goroutine 생성과 API 워밍업은 타이머 밖입니다.
  신규 문자열 생성, 실제 호출, 값 검사, 시각 읽기와 통계 갱신은 처리량/할당 측정에 포함합니다.
  개별 호출 지연은 키 생성 이후부터 측정합니다.
- 공통 글로벌 per-request 카운터 락은 없습니다. 클라이언트별 통계를 완료 후 합칩니다.
- 세 샤딩 구현은 같은 시나리오에서 동일 maphash seed를 사용합니다.
  Go의 maphash seed는 재실행 때 바뀝니다. 스케줄과 실제 병합 타이밍도 고정하지 않습니다.
- 시간 기준의 Go 자동 보정으로 구현별 N이 달라질 수 있습니다. 같은 N일 때 클라이언트별
  키 선택 prefix는 동일하지만 모든 실행의 전체 요청열이 완전히 동일한 것은 아닙니다.
  실제 unique/op·dochan/op 및 표본별 N을 원본/집계에 보존합니다.

### 백엔드 두 종류

- **CPU**: 결과에 반영되는 데이터 의존 1,024회 정수 연산. 짧은 계산/완료 경로와
  많은 키의 레지스트리 경합을 함께 측정합니다.
- **IOMixed**: 키 token이 10의 배수면 5ms, 나머지는 1ms의 `time.Sleep`.
  같은 키는 항상 같은 지연과 결과를 갖습니다. 재사용 풀 전체 기준 느린 키는 약 10%지만,
  인기 분포와 병합에 따라 느린 실행의 실제 비율은 달라집니다.
  sleep은 I/O 대기 대용이며 실제 네트워크·DB·백엔드 동시성 제한은 없습니다.
  OS 타이머/스케줄러에 의해 실제 지연이 늘어날 수 있어 실제 백엔드 시간도 측정합니다.

## 지표와 시계 한계

- requests/s: 벤치마크 경과 시간 대비 완료 요청 수.
- ns/op: 전체 경과 시간 / 요청 수. 동시 처리되므로 **개별 요청 지연이 아닙니다**.
- backend/op: 실제 함수 실행 수 / 요청 수. `1 - backend/op`가 실행 억제 비율입니다.
- shared/op: Shared=true 결과 비율. 최초 생산자도 shared가 될 수 있어 위 비율의 보수가 아닙니다.
- unique/op, dochan/op: 실제 입력 혼합 비율. errors/op는 잘못된 값/오류 수이며 반드시 0이어야 합니다.
- backend-mean-ns, backend-p95-ns, slow-backend/op: 실제 함수 경과 시간 및 5ms 요청 실행 비율.
- p50/p95/p99: 모든 요청의 호출 지연 히스토그램. 각 2의 거듭제곱 구간을 16분할하여
  bucket 상한을 보고합니다. 히스토그램 자체의 반올림은 최대 약 6.25%입니다.
  집계의 중앙값 p99는 각 실행 p99의 중앙값이며 전체 실행을 합친 p99가 아닙니다.
- latency-zero/op, backend-zero/exec: 시각 차이가 0으로 기록된 요청/실행 비율.
  0ns가 실제 비용 0 또는 즉시 실행을 뜻하지 않습니다.

시계 진단 원본: [windows-arm64-service-clock.txt](testdata/benchmarks/windows-arm64-service-clock.txt).
이 Windows ARM64 환경에서 time.Now 연속 읽기 100,000회 중 99,998회가 같은 시각이었고,
관측된 최소 양의 차이는 637µs였습니다. 짧은 CPU 실행의 세밀한 지연을 구분하지 못합니다.
따라서 **이 환경의 CPU p50/p95/p99로 우열을 판단하지 않습니다**.
IOMixed의 밀리초 지연도 시계·스케줄러 오차를 갖습니다. 6.25%는 히스토그램 반올림만의
한계이며 전체 측정 오차의 상한이 아닙니다. 처리량은 Go testing.B가 관리하는 전체
경과 시간으로 측정합니다. 설치된 Go 1.27.1의 testing_windows.go와 benchmark.go를
확인했으며, B의 전체 시간은 일반 time.Now와 별도로 QueryPerformanceCounter를 사용합니다.

## 해석

1. **혼합 상황에서도 CPU 처리량 중앙값은 WG가 Channel보다 높았습니다.**
   6개 CPU 조합에서 약 4.4–37.6% 높았고, Channel의 추가 할당도 남아 있습니다.
   다만 Uniform64 WG 범위는 2.75–3.61M req/s, Zipf64 WG는 1.60–2.70M req/s로
   변동이 큽니다. 특정 중앙값 차이를 보편적인 개선율이나 통계적 우세로 단정하지 않습니다.
2. **I/O 대기가 지배하면 WG/Channel/Cond 차이가 작아졌습니다.** WG와 Channel의
   처리량 중앙값 차이는 약 -1.6%부터 +4.6%이며 범위가 겹칩니다. p99도 비슷한
   밀리초 구간입니다. 이 결과로 Cond가 항상 병목이라거나 Channel이 반드시
   유리하다고 결론 내릴 수 없습니다.
3. 1,024 클라이언트 IOMixed에서 WG 처리량 중앙값은 x/sync보다 약 12–20% 높았습니다.
   64 클라이언트에서는 네 구현이 훨씬 비슷했습니다. CPU 부하의 큰 샤딩 이점을
   실제 외부 I/O 서비스 전체의 개선율로 가져오면 안 됩니다.
4. **처리량과 백엔드 실행량은 함께 봐야 합니다.** 예를 들어 CPU/Hot32/1024에서
   WG backend/op는 0.8460, x/sync는 0.3943입니다. 전역 락 대기와 스케줄링도 중복이
   겹치는 시간을 바꾸므로 함수 실행 수가 고정된 순수 대기 primitive 비교가 아닙니다.
