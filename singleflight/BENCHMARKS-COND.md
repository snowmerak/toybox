# Cond 구현의 초기 벤치마크 (과거 기록)

이 문서는 WaitGroup 전환 전 측정을 보존한 기록입니다. 현재 구현과 같은 실행에서
다시 비교한 결과는 [BENCHMARKS.md](BENCHMARKS.md)를 참고하세요.
아래 재현 명령은 당시 소스를 기준으로 하며, 현재 소스에서는 세 구현을 비교합니다.

## 측정 환경

- 측정일: 2026-10-03
- Go: `go1.27.1 windows/arm64`, `CGO_ENABLED=0`
- CPU: Snapdragon X Plus X1P42100 (Qualcomm Oryon), 8코어 / 8 논리 프로세서
- 비교 대상: `golang.org/x/sync/singleflight v0.23.0`
- 자체 구현: 기본 255개 샤드, `maphash.String`, 샤드별 map/mutex,
  동기 중복 대기에 필요할 때 생성하는 `sync.Cond`
- 각 케이스를 `GOMAXPROCS=1,8`에서 각각 500ms씩 5회 측정했습니다.
  오류와 반환값을 확인하며, 초기화는 ColdGroup을 제외하고 측정에서 뺐습니다.
- 원본 출력: [windows-arm64.txt](testdata/benchmarks/windows-arm64.txt)
- 측정 소스는 이 작업의 미커밋 상태이며, 구현과 벤치마크 파일의 SHA-256을
  [source-sha256.txt](testdata/benchmarks/source-sha256.txt)에 기록했습니다.
  원시 표본의 중앙값·최소·최대는 [summary.json](testdata/benchmarks/summary.json)에 보존했습니다.

```powershell
go test ./singleflight -run '^$' -bench 'Benchmark(Serial|Parallel|DoChan|ColdGroup)$' -benchmem -benchtime=500ms -count=5 '-cpu=1,8'
```

## 처리 비용: 5회 중앙값 (ns/op)

값이 작을수록 좋습니다. 병렬 케이스의 ns/op는 전체 호출 수 기준 처리 비용이며,
개별 요청의 응답 지연 시간이나 p95/p99가 아닙니다. `8` 열에서도 Serial과
ColdGroup은 동시 호출 없이 실행됩니다.

| 케이스 | 자체 / 1 | x/sync / 1 | 자체 / 8 | x/sync / 8 | 8에서 x/sync ÷ 자체 |
|---|---:|---:|---:|---:|---:|
| Serial / 짧은 키 | 106.0 | 180.9 | 123.4 | 136.1 | 1.10× |
| Serial / 4096바이트 키 | 575.1 | 239.7 | 552.4 | 234.6 | 0.42× |
| Do / 워커별 독립 키, 즉시 반환 | 113.4 | 139.5 | 50.70 | 657.4 | 12.97× |
| Do / 256개 키 순환, 즉시 반환 | 123.2 | 116.1 | 88.78 | 754.4 | 8.50× |
| Do / 단일 키, 즉시 반환 | 110.4 | 114.9 | 762.8 | 687.2 | 0.90× |
| Do / 단일 키, Gosched | 234.9 | 236.6 | 934.3 | 747.9 | 0.80× |
| Do / 16개 키 순환, Gosched | 284.5 | 303.2 | 351.3 | 858.6 | 2.44× |
| Do / 워커별 독립 키, CPU 작업 | 1447 | 1444 | 273.6 | 1304 | 4.77× |

| DoChan / 워커별 독립 키, 즉시 반환 | 619.1 | 616.4 | 263.8 | 1242 | 4.71× |

`Gosched`는 중복이 겹칠 기회를 만들기 위한 스케줄러 양보이며,
실제 I/O 대기 시간을 흉내 낸 것이 아닙니다. CPU 작업은 데이터 의존적인
1024회 정수 연산 루프입니다. 독립 키 케이스는 워커마다 서로 다른 하나의 키를
반복 사용합니다. 순환 키 케이스는 동일 키 목록을 워커별 시작점만 달리해
순회하며, 랜덤 분포나 Zipf 분포가 아닙니다.

## 중복 억제와 할당 (8, 각각의 중앙값)

`backend/op`는 요청 하나당 실제 함수 실행 횟수이며 낮을수록 많이 병합된
것입니다. `shared/op`는 공유 결과를 받은 요청 비율입니다. 최초 호출자도
Shared가 true일 수 있으므로 두 값은 합계가 1인 관계가 아닙니다.

| 케이스 | backend/op 자체 / x/sync | shared/op 자체 / x/sync | B/op 자체 / x/sync |
|---|---:|---:|---:|
| Do / 독립 키, 즉시 반환 | 1.000 / 1.000 | 0 / 0 | 80 / 80 |
| Do / 256개 키 순환 | 0.9908 / 0.9791 | 0.01723 / 0.03946 | 79 / 78 |
| Do / 단일 키, 즉시 반환 | 0.6560 / 0.6484 | 0.4769 / 0.5344 | 60 / 51 |
| Do / 단일 키, Gosched | 0.2479 / 0.2264 | 0.9643 / 0.9807 | 33 / 18 |
| Do / 16개 키 순환, Gosched | 0.4465 / 0.6267 | 0.8325 / 0.5939 | 53 / 50 |
| Do / 독립 키, CPU 작업 | 1.000 / 1.000 | 0 / 0 | 88 / 88 |
| Do / 단일 키, CPU 작업 | 0.2592 / 0.2105 | 0.9469 / 0.9675 | 36 / 18 |
| DoChan / 독립 키 | 1.000 / 1.000 | 0 / 0 | 312 / 296 |
| DoChan / 단일 키, Gosched | 0.2458 / 0.2089 | 0.9611 / 0.9898 | 212 / 203 |

- 중복 없는 `Do`는 두 구현 모두 80 B/op, 1 alloc/op입니다.
- 독립 키 CPU 케이스는 반환 uint64의 interface boxing을 포함해
  두 구현 모두 88 B/op, 2 allocs/op입니다.
- 독립 키 `DoChan`은 두 구현 모두 5 allocs/op이고, 자체 구현의
  goroutine 호출 인자 등을 포함한 총 할당은 16 B/op 더 큽니다.
- ColdGroup은 자체 16,672 B/op / 259 allocs/op, x/sync는
  352 B/op / 4 allocs/op입니다. 255개 map을 모두 생성하는 초기 비용이므로
  요청마다 새 Group을 만들면 안 됩니다.
- Go 벤치마크 출력의 `allocs/op`는 정수로 표시됩니다. 중복 병합 케이스에서
  0 allocs/op라고 표시되어도 할당이 전혀 없다는 뜻은 아닙니다.

## 결론과 한계

1. **여러 키의 병렬 호출에는 샤딩의 이점이 뚜렷합니다.** 독립 키에서는
   병합 비율이 양쪽 모두 0이므로, 약 13배 차이를 중복 억제량 차이로 설명할
   수는 없습니다. 단일 전역 mutex의 경합을 줄이는 구조가 유리한 결과입니다.
2. **하나의 핫 키에는 샤딩이 도움이 되지 않습니다.** 이 실험의 동기 `Do`는
   x/sync보다 약 11–25% 느렸습니다. Cond의 별도 할당과 깨어난 대기자의
   샤드 mutex 재획득이 추가되는 구조입니다. 다만 이번 비교는 샤딩·대기 방식
   등을 함께 바꾼 결과이므로 Cond 하나만의 영향을 분리해 입증한 것은 아닙니다.
3. **긴 키와 초기화는 비용이 큽니다.** 4096바이트 키는 샤드 선택용 추가
   해시 때문에 약 2.35배 느렸고, 새 Group의 첫 호출은 약 51배 느렸습니다.
   재사용할 장수명 Group과 짧은 키를 주로 쓰는 경우에 적합합니다.
4. **병합이 발생한 케이스는 처리 속도만으로 판단하면 안 됩니다.**
   스케줄링과 실행 속도가 달라지면 호출이 겹치는 비율도 달라집니다.
   특히 16개 키/Gosched는 실제 함수 실행량도 크게 다릅니다.
5. 일반 Windows 개발 환경에서 순차 측정했으며 CPU 주파수·백그라운드 부하를
   고정하지 않았습니다. 5회 중앙값과 범위를 보고했지만 `benchstat`가 설치되어
   있지 않아 통계적 유의성 검정은 하지 않았습니다. 작은 차이나 범위가 겹치는
   차이는 개선으로 단정하지 않습니다.
6. 이는 마이크로벤치마크이며 실제 서비스의 지연 분포, 고카디널리티 메모리,
   긴 작업, 대량 대기자, 장시간 부하를 검증하지 않았습니다. 255개가 최적이라는
   주장도 아닙니다. `BenchmarkShardCount`로 별도 샤드 수 실험을 할 수 있습니다.

## 정확성 검증 상태

- `go mod tidy`, `go build ./...`, `go vet ./...`: 통과.
- `go test ./... -count=20 -shuffle=on -timeout=120s`: 통과.
- `go test ./... -coverprofile=...`: 문장 커버리지 97.2%.
- `golangci-lint 2.14.0 run --no-config ./...`: 0 issues.
  활성 검사: errcheck, govet, ineffassign, staticcheck, unused.
- `go test -race ./...`: Windows ARM64 미지원 오류로 **검증하지 못함**.
  지원하는 환경에서 race 테스트를 추가로 실행해야 합니다.
- `govulncheck`: 설치되어 있지 않아 실행하지 못했습니다.

동시성 테스트 통과는 검사한 실행에 대한 증거이며 모든 스케줄에서의 안전성을
증명하지 않습니다. 커버리지 역시 정확성 보장이 아닙니다.
